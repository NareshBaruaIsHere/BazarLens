# BazerLens frontend handoff

## 1. Delivered frontend and run commands

Frontend only. `BazarLens.Server/` is unchanged. React 19, Vite 8, JavaScript/JSX, plain CSS, Context, React Router, inline SVG/CSS charts. The only added direct dependency is `react-router-dom` (see package-lock.json for the exact installed version).

```sh
cd bazarlens.client
npm install
npm run dev
npm run lint
npm run build
node tests/mockApi.test.mjs
node tests/render.test.mjs
npm run preview
```

Use `npm.cmd` on Windows if PowerShell blocks `npm.ps1`. Development uses port 7864. Vite reuses existing Visual Studio HTTPS certificates when present and otherwise uses localhost HTTP; it no longer generates certificates or requires dotnet to run the mock frontend. Production output is generated by Vite in `dist/`; never edit it manually.

Implementation plan: `FRONTEND_PLAN.md`.

## 2. Routes and role requirements

- `/`: redirects to `/login`, `/dashboard`, or `/admin` according to the restored account.
- Guest account flows: `/login`, `/signup`, `/forgot-password`. Signed-in accounts redirect to their dashboard.
- Public: `/statistics` (approved price comparisons and historical chart, no login), `/about`, `/privacy`, `/terms`, `/help`, `/access-denied`.
- Active authenticated account (user, agent or admin): `/dashboard`, `/prices`, `/trends`, `/submissions`, `/alerts`, `/analytics`, `/profile`, `/settings`.
- Active administrator only: `/admin`, `/admin/users`, `/admin/submissions`, `/admin/products`, `/admin/markets`, `/admin/analytics`, `/admin/profile`, `/admin/settings`.
- Any unmatched path renders a 404 page.
- `/submissions?create=1` opens the contribution dialog.

An unauthenticated protected visit redirects to login. A regular user visiting an admin route redirects to access denied. BrowserRouter supplies real URLs, history and back/forward support. Deployment must rewrite application URLs to index.html. The service also validates ownership/roles, but browser-only checks are not a production security boundary.

## 4. Models and field definitions

Database key: `bazerlens_mock_db_v1`. Top-level object: `{version:1, users:[], products:[], markets:[], submissions:[], alerts:[], settings:{}, activity:[]}`. Seed only when absent. IDs are opaque strings (seed IDs are readable; new IDs are UUIDs). Timestamps are ISO 8601 UTC. Observation `date` is YYYY-MM-DD. Prices are numbers in BDT, rounded to two decimals. Array responses are unpaginated in this prototype.

- **User**: `id`, `name` (display/full name), `email` (normalized lowercase, unique), `password` (mock only), `city`, `area` (thana), `avatarUrl` (optional HTTP(S)), `role` (`user|agent|admin`), `status` (`active|blocked`), `createdAt`. Safe service responses omit `password`. User-list rows add `contributions` (integer).
- **Product**: `id`, `name` (unique case-insensitively), `category`, `unit` (default unit, e.g. kg/dozen), `active` (boolean), `createdAt`. Unit cannot change once referenced by submissions.
- **Market**: `id`, `name`, `area`, `district`, `division`, `active`, `createdAt`. Name + area identifies a unique market in normal CRUD.
- **Submission**: `id`, `userId`, `productId`, `marketId`, `area` (market-area snapshot), `unit` (product-unit snapshot), `price`, `date`, `note` (optional, at most 1000 characters), `evidenceUrl` (optional HTTP(S)), `status` (`pending|verified|rejected`), `rejectionReason`, `createdAt`, `updatedAt`, `history` (array of `{status,reason,reviewerId,at}`). General-user submissions are pending. Normal agent submissions are automatically verified; unusual agent submissions or insufficient baselines remain pending and flagged. See section 19 for the screening contract. Reviewed rows are immutable to contributors. List rows also include `product`, `category`, `market`, `user` display strings.
- **Alert**: `id`, `userId`, `productId`, `area` (empty means all areas), `direction` (`above|below`), `targetPrice`, `enabled`, `createdAt`. List responses also include `product` and `unit`.
- **Settings**: dictionary keyed by user ID; each value has `defaultArea` (empty means all), `emailAlerts`, `inAppNotifications`, `compactTables` (booleans). Defaults are empty, false, true, false respectively.
- **Activity**: `id`, `userId`, `message`, `createdAt`. Records account/profile/password, submission/review, catalog/user and import activity. They are a demo activity feed, not a tamper-proof audit log.
- **PriceRow**: enriched submission fields from the latest observed day plus composite `id`, `average`, `lowest`, `highest`, `date` and `history` (verified observations in this product/market/unit group). Current aggregates use observations on the latest available date per group. Historical data remains in `history`. Never combine unlike units.
- **TrendPoint**: `{date,value}`; mean of verified observations on that day for the selected product/area/date window.
- **Notification**: `{id,message,emailPreview}` for each enabled user alert whose target is crossed by a current market average. No notification persistence/read state or email delivery. In-app preference suppresses these results; email preference adds visible preview labels.
- **Summary**: `{total,pending,verified,rejected,products,markets,prices:PriceRow[],notifications:Notification[],recent:EnrichedSubmission[]}`. Admin also gets `users,activeUsers,blockedUsers`. User counts/recent records are scoped to the user; prices remain community-wide. Admin counts cover all records.
- **Analytics**: `{total,verifiedRate,pending,byStatus,byProduct,byArea,byMonth,contributors,userGrowth,prices,rejected,flagged,activity}`. Group series are `{label,value}[]`; verifiedRate is 0–100. User growth is admin-only; other data is scoped by role. Flagged contains pending rows requiring screening review; rejected contains rejected rows. The admin summary displays both.
- **DatabaseStats**: `{users,products,markets,submissions,alerts,activity}` integer record counts.

## 5. Service conventions

All page data access goes through `src/services/mockApi.js`; pages never access browser storage. Methods return Promises, simulate 350 ms latency, return cloned data, and throw `Error` with useful messages. There are no random failures. Mutations write one database document and broadcast `bazerlens-data`; the data hook refreshes affected views. HTTP integration should preserve these exported method names and direct return shapes.

The table below lists every method and its matching proposed HTTP endpoint. `save*` chooses POST when `id` is absent and PUT when present. Existing pages pass some enriched response fields back to save methods; adapters must whitelist the documented writable fields. Infer account IDs from authenticated identity, never trust a supplied userId.

## 6. Exact HTTP contract

All URLs below are relative to the API origin and already include `/api`. JSON request/response content type. All successful JSON bodies are direct values, without a `{data:...}` wrapper. Use 200 for reads/updates/login, 201 for creates, and 200 `{success:true}` for deletes/logout/reset-password/change-password. Protected endpoints may return 401 (no active session) and 403 (insufficient role/ownership); all can return 500 with a safe message.

Error body: `{ "message": "Human-readable explanation", "code": "VALIDATION_ERROR", "errors": { "field": ["detail"] } }`. `errors` is optional. The fetch adapter throws an Error using `message`; optional code/field errors may be retained for later UI enhancement. Expected domain errors below are in addition to common authentication/server errors.

Request aliases (all listed fields are exact):

- **AccountInput** = `{name,email,city,area,avatarUrl?}`.
- **SignupInput** = `{name,email,city,area,password,confirmPassword,agreeTerms}`.
- **UserInput** = `{name,email,city,area,avatarUrl?,role,status,password?}`; password required only on creation. Role/status are admin-only.
- **ProductInput** = `{name,category,unit,active}`.
- **MarketInput** = `{name,area,district,division,active}`.
- **SubmissionInput** = `{productId,marketId,unit,price,date,note?,evidenceUrl?}`. Server derives area from market. Contributor cannot write status/reviewer/userId/history/screening/flagged; server derives them.
- **AlertInput** = `{productId,area,direction,targetPrice,enabled}`.
- **SettingsInput** = `{defaultArea,emailAlerts,inAppNotifications,compactTables}`.
- **Backup** = the complete version 1 database object defined above; demo environment only.

## 7. Suggested PostgreSQL schema and relationships

Include `agent` in the users role constraint. Submission reviews permit a null reviewer_id only for source=automatic, with a mandatory policy identifier; manual reviews require a reviewer FK. Persist submission screening metadata and flagged state (section 19) in typed columns or validated JSONB.

Use UUID primary keys in production, timestamptz for event times, date for observations, numeric(12,2) for prices. Seed IDs must be remapped if importing demo records to UUID tables.

- `users`: id, display_name, normalized_email UNIQUE, password_hash, city, area, avatar_url, role, status, created_at, updated_at. Check role/status enums. Never store raw passwords.
- `products`: id, name, category, default_unit, active, created_at. Unique lower(name).
- `markets`: id, name, area, district, division, active, created_at. Unique normalized(name,area).
- `submissions`: id, user_id FK users RESTRICT, product_id FK products RESTRICT, market_id FK markets RESTRICT, area_snapshot, unit_snapshot, price CHECK >0, observed_date, note, evidence_url, status, rejection_reason, created_at, updated_at, concurrency_version.
- `submission_reviews`: id, submission_id FK submissions, reviewer_id FK users RESTRICT, status, reason, reviewed_at. Immutable audit entries. Require a reason for rejection.
- `alerts`: id, user_id FK users CASCADE, product_id FK products RESTRICT, area nullable, direction, target_price CHECK >0, enabled, created_at.
- `user_settings`: user_id PK/FK users CASCADE, default_area nullable, email_alerts, in_app_notifications, compact_tables.
- `activity_records`: id, actor_id FK users, event_type, entity_type, entity_id, display_message, created_at. Production audit retention should not cascade-delete historical review evidence.
- `refresh_sessions`: id, user_id FK users, token_hash, expires_at, revoked_at, rotated_from_id, created_at; if using cookie refresh tokens.
- `password_reset_tokens`: id, user_id, token_hash, expires_at, used_at.
- Optional production `notifications`: id, user_id, alert_id, observed_price_group, message, created_at, read_at, delivered_at, deduplication_key.

Index submissions on (product_id, market_id, observed_date, status), (user_id, created_at), and (status, created_at). Index alerts by (user_id,enabled), reviews by submission_id and activity by actor/time. Use a transaction and locking/concurrency token for approval and last-active-admin checks. Keep historical market area/unit snapshots unchanged when catalog labels change.

## 8. Production authentication and authorization

Use ASP.NET Identity or an equivalent maintained password hasher (Argon2id or appropriate configured Identity hashing); no frontend hashing scheme substitutes for server hashing. Enforce unique normalized emails, rate limits, lockout policy and sensible password checks. Short-lived JWT access tokens may be held in memory; use rotated, revocable refresh tokens in Secure, HttpOnly, SameSite cookies, or use secure server sessions/cookies throughout. Avoid persistent browser storage for production bearer tokens. Protect cookie-authenticated mutations from CSRF. Verify JWT issuer/audience/signature/expiry and enforce roles/ownership on every endpoint.

`remember` controls refresh/session cookie lifetime, not password persistence. Blocking an account must invalidate refresh sessions and reject protected operations. Logout revokes the session and clears cookies. On reload, `/auth/session` restores identity. Role changes must affect server authorization immediately; never trust UI visibility.

Production reset differs intentionally: `/auth/forgot-password` returns generic success without revealing existence and sends a single-use expiring token; `/auth/reset-password` requires `{token,password,confirmPassword}`. Replace the demo two-step screen with token-link handling. Production signup should verify email and display real published terms. Add OAuth through a server/provider flow; remove the informational Google toast only when connected.

Use HTTPS for real accounts. Trust a development certificate through the normal OS/browser procedure. ## 11. Evidence and upload considerations

Current evidence is an optional HTTP(S) URL opened in a new tab with noreferrer. Avatar URLs load external resources. No binary uploads exist. Production uploads should use authenticated presigned object-store uploads or a constrained upload endpoint with size/type validation, malware scanning, safe content disposition, randomized object names, retention/deletion rules, ownership checks and expiring read URLs. Do not fetch arbitrary evidence URLs server-side without SSRF defenses. Do not trust extension or browser MIME alone. Avoid exposing receipts with personal information. A production Content Security Policy should constrain avatars and evidence handling.

## 12. Shared validation and invariants

- Required names/location/category text: trimmed, nonempty, max 120 chars; email max 254 and syntactically valid, normalized lowercase, unique.
- Demo password: 8–128 chars; confirmation must match. Change password validates current password. Production policy must be enforced on the server independently.
- Price/target: finite numeric value >0 and <=1,000,000 BDT, rounded to two decimals. Unit must match the product; area derives from the selected market.
- Observation date: valid calendar YYYY-MM-DD, not later than local today; define Asia/Dhaka consistently in production rather than trusting client timezone.
- URLs: HTTP(S) only; optional empty strings allowed. Notes max 1000; rejection reason required, max 1000.
- New submissions require active catalog records. Only owner + pending permits edit/delete. Only admin + pending permits review; reject requires reason.
- Only own alerts/preferences/profile are writable by users. Profile updates ignore role/status fields. Signup cannot grant admin or blocked state.
- Current admin cannot block/delete themselves. Never remove the last active admin. Users referenced by contributions/reviews must be blocked instead of deleted.
- Products referenced by submissions/alerts and markets referenced by submissions cannot be deleted. Deactivate instead. Referenced product units are immutable.
- Disabled buttons while requests run reduce double submission; production must additionally implement transactional checks/idempotency as appropriate. Agents cannot manage accounts or grant their own role; automatic approval is determined from the authenticated current role and service-owned screening metadata.

## 17. Known prototype limits

Local storage is not durable, multi-device, concurrent transactional storage or secure authorization. Anyone with browser access can edit the database/session. Cross-tab refresh is supported, but simultaneous cross-tab writes can still overwrite each other. All prices are mock data. No actual email, Google OAuth, file upload, JWT, refresh token or backend connection is implemented. Data tables are unpaginated. The map is illustrative and shows seed-market locations only; averages are available in the adjacent chart/table for other markets. Email preferences create visible previews, not email delivery. Activity is a demo feed, not a compliance audit trail. Invalid/corrupt storage surfaces an error rather than silently replacing user changes; clear site storage or restore a valid backup as appropriate.

## 19. README.txt alignment: agents, screening and public statistics

This section extends the original frontend specification using the root README. Keep the frontend-only restriction: PostgreSQL remains a backend implementation task. See RUNNING.md for verified startup commands and the precise current server limitations.

- Admin Users supports assigning, adding, editing, filtering, blocking and unblocking `agent` accounts. Signup remains `user`; profiles cannot self-promote. Agents use `/dashboard`, `/submissions` and the other authenticated routes, with the role shown in the profile menu/topbar. Agents cannot access admin services or routes.
- New and edited pending submissions undergo screening in `src/services/priceScreening.js`. Only active authenticated agents can get automatic approval. General-user/admin contributions remain pending regardless of screening result, preserving the original manual community-review workflow.
- The policy `market-median-v1` requires at least three distinct independently verified observation dates in the 30-day inclusive interval ending on the submitted observation date. It uses the same product, unit and market, excludes the current row, the contributor?s own records, and automatically approved records. This avoids using an agent?s repeated automatic submissions to move their own baseline. Compute a daily average, then the median of these daily values. A deviation strictly greater than 25% in either direction is unusual; exactly 25% is normal.
- The 25% threshold, 30-day window and minimum three dates are explicit prototype assumptions because the README supplies no numeric policy. Real thresholds and independence/trust criteria must be defined and enforced by the backend team; this is not a statistical fraud detector.
- `screening` is `{policy,thresholdPercent:25,sampleDays,baseline:number|null,deviationPercent:number|null,checkedAt,decision,reason}`. Decision is `normal|unusual|insufficient-data|auto-approved`. `flagged` is true for unusual/insufficient data. Do not accept these values from submission request bodies.
- Auto-approved rows become `verified` and append `{status:"verified",reviewerId:null,source:"automatic",at,reason}` to history. They immediately enter approved prices, public comparisons and analytics. They are read-only like manually approved rows. Admin review handles pending flagged reports; review retains the screening explanation as an audit snapshot.
- Old records without screening fields remain valid and are identified as legacy/manual. They are not retroactively approved. No stored accounts or contributions are reset by this update. Backup validation accepts agents and validates new screening/automatic-history metadata, while retaining legacy backup compatibility.
- Public `/statistics` filters approved price aggregates by product and area and shows a single-product historical chart. `getPublicStatistics(filters)` is anonymous and returns explicitly projected values only. PublicPriceRow is `{id,productId,product,category,marketId,market,area,unit,date,average,lowest,highest}`. No contributor IDs/names/emails, evidence, notes, review history or raw submission arrays are returned. Empty product filter shows all products in the table and the first catalog product in the clearly labelled chart. The backend must use the same public projection.
- New signups receive a default price-filter area matching their thana when available, otherwise the first market in their city/district, otherwise all areas. Settings can override it.
- Additional checks: assign/demote an agent, deny admin access, normal auto-approval and audit source, unusual/insufficient-data flags, re-screen an edited pending record, immutable verified rows, flagged admin filters/analytics, private-data exclusion from public output, and backup roundtrip with automatic review history.
